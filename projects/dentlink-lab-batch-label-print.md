### 3·4 선택과 일괄 출력의 추천 구현

- 기존 목록/검색/필터/API 페이지네이션/상세 진입을 유지하고 좌측 선택 열과 표 위 요약바를 추가했다. 처음에는 접힌 선택 영역이며 펼치면 번호·환자/치과/운송번호와 개별 제외를 보여준다. 영역 내부 스크롤로 표 전체를 계속 밀어내지 않도록 했다. 현재 페이지 선택과 전체 해제를 제공한다. ‘전체 검색 결과 선택’은 제공하지 않는다.

### 5 생성 완료→출력 연결의 범위 조정

- createShipment 응답은 생성 배송 ID가 없는 boolean이다. 기존 완료 이벤트의 sourceId는 배송 상세 이동에 사용하는 정확한 ID다. 여러 생성 요청의 결과를 치과명/시각 등으로 추정해 자동 묶으면 다른 작업을 잘못 출력할 위험이 있어 자동 묶음을 도입하지 않았다.
- 기존 배송 진행 플로팅의 COMPLETED 항목에 ‘출력 목록에 추가’를 추가했다. sourceId로 배송 상세를 재조회하고 ID/labelUrl/생성 상태를 확인한 경우만 같은 배송 선택 모음에 추가한다. 이미 추가한 항목은 재추가를 막는다. QR 스캔 화면에도 선택 모음을 표시하여 배송 목록을 다시 검색하지 않고 모아 출력할 수 있다.

### 5. QR 스캔 배송 생성 후 출력 연결

- 작업 끊김과 재탐색을 줄이는 목적·서버 비동기 생성이라는 제약은 이해했다. 실제 완료 이벤트가 이번 요청의 어떤 배송에 대응하는지는 아직 상세 확인하지 않았다.
- FE 단독 가능성은 조건부다. 기존 응답/알림/조회에서 생성 묶음의 배송ID, 완료/실패, 출력 URL 준비 상태를 확인할 수 있으면 연결 후보가 된다. 그 정보가 부족하면 추가 계약 검토 또는 범위 축소가 필요할 수 있다.
- 검토 후보: 생성한 대상의 준비 상태를 유지하고, 출력 가능한 대상만 묶어 출력 동작을 제공한다. 전부 완료를 기다릴지, 준비된 것부터 출력할지, 실패분을 어떻게 남길지는 정책 미정이다. 일반 웹의 팝업/인쇄창 제약과 Electron 자동출력은 별도다.
- 의견: 개선 효과는 클 수 있지만 자동으로 인쇄창부터 띄우는 것으로 해결하지 않는다. 기존 완료 신호와 데이터 식별 가능성을 먼저 확인하고 UI를 정한다.

### 6. 여러 프린터·용지 크기에 맞춘 출력

- 추가 설명으로 사용 목적이 구체화됐다. 현장에서는 배송 라벨 세트의 앞부분과 다음 문서를 다른 용지/프린터로 보낸다. 정확한 장치 수·모델·OS·용지·안내문 필요 여부는 아직 없다.
- 일반 웹에서 내용 분리와 각각의 인쇄 대화상자 호출은 가능하다. iframe이 프린터 선택 권한을 추가하지는 않는다. 보통의 브라우저 설치만으로 자동으로 두 프린터를 지정하는 흐름은 표준 window.print 범위를 넘는다.
- Electron API로 두 작업을 지정 프린터에 보내는 구조는 가능하다. 기본 프린터 하나를 바꾸는 방식보다 앱에 문서 종류별 프린터/용지 매핑을 저장하는 구성이 후보다. 이는 설계 제안이며 저장 범위와 UI는 미확정이다.
- 의견: 실제 프린터2대의 출력 검증을 거친 후 판단할 가치가 있다. 정확한 용지와 인쇄 품질 확인 전에는 현장 사용 성공으로 말하지 않는다. 라이브러리 성공 콜백/스풀 접수를 실제 종이가 나온 증거로 취급하지 않는다.

#### 방법 후보: Electron과 현장 운영 조건

- **사용자 조건:** 개발자가 현장에 상주하지 않는다. 초기 세팅을 제대로 하고 현장 직원의 불편과 개입을 최소화해야 한다. 다른 곳/다른 개발자가 웹 서비스를 업데이트해도 설치된 앱이 따라가지 못해 출력이 중단되면 곤란하다. 이는 도입 판단의 핵심 요구이며, 단순 인쇄 API 지원만으로 채택하지 않는다.
- 기술적 가능성은 높고 JS/TS로 구현 가능하다. 그러나 현재 이해 수준은 구조 검토 단계이며 현장 설치 권한, 지원 OS, 프린터/드라이버, 네트워크, 배포/장애 대응 소유자가 미확정이다. 초기 설정1회로 이후 관리가 영구히 없어지는 것은 보장할 수 없다.
- 온라인 웹을 불러오는 앱은 일반 UI 변경을 웹 배포로 받을 수 있지만, 열린 화면이 배포 즉시 안전하게 교체되거나 인쇄 연결이 자동으로 호환되는 것은 아니다. 강제 새로고침 없이 다음 안전한 진입/갱신에서 반영할 방식을 검토한다. 오프라인 운영까지 자동 제공하지 않는다.
- 권고 구조: 자주 바뀌는 업무 화면·출력 콘텐츠는 웹이 소유하고, 앱은 프린터 조회/설정·정해진 형식의 인쇄 요청 처리만 담당한다. 인쇄 연결은 DOM 위치/버튼 텍스트를 찾아 조작하는 방식이 아니라 명시적 함수·데이터 계약으로 유지하는 편이 좋다.
- 웹↔앱의 연결 규격과 지원 기능/버전을 확인한다. 일반 웹 배포는 설치된 앱의 기존 인쇄 요청도 계속 지원하도록 하고, 새 앱 기능이 필요한 변경은 앱을 먼저 배포한 뒤 지원되는 현장에서만 사용한다. 새 웹이 배포됐다고 모든 현장 앱도 최신이라고 가정하지 않는다.
- 다른 개발자가 변경하는 웹 릴리스에도 인쇄 연결과 출력 레이아웃의 호환 검사 책임이 있어야 한다. 특정 개발자만 기억하는 비공식 연동은 유지 부담이 커진다. 이는 팀 공통 개발 문서로 승격할 후보이나 아직 제품 문서 변경 승인은 없다.
- 자동 업데이트는 다운로드와 적용을 구분한다. 백그라운드로 업데이트를 준비할 수 있지만, 출력/대기 작업 중 즉시 종료·재시작하지 않는다. 작업을 마친 앱 종료/다음 실행 같은 안전한 시점을 선택하고 장기간 켜둔 PC의 업데이트 지연도 다룬다. 현장 설치 권한·보안 프로그램·네트워크에 따른 실제 갱신 성공은 검증해야 한다.
- 업데이트 실패만으로 기존 정상 출력을 막지 않도록 설계하되, 호환 불가/필수 보안 갱신은 별도 판단이 필요하다. 무조건 구버전을 무기한 지원하거나 모든 장애에서 자동 복구된다고 약속하지 않는다.
- 문서별 프린터/용지 설정을 앱 업데이트 후 보존하고, 장치가 사라지거나 바뀌면 알아볼 수 있게 해야 한다. 두 출력 중 하나만 실패하면 성공분을 다시 찍지 않도록 작업별 결과·재출력 흐름을 구분한다. 출력 성공의 실제 판정 가능 범위는 드라이버별로 확인한다.
- 장애 시 기존 브라우저 수동 출력을 유지하는 대안, 버전/인쇄 오류를 원격에서 확인할 수 있는 수단, 문제 배포의 복구 절차가 운영 후보다. 구체적 로그 수집/원격제어/외부 도구 도입은 별도 미승인 범위이며 고객·주문정보를 임의 수집하지 않는다.
- 앱 런타임 보안 업데이트와 코드 서명/인증서·배포 저장소 관리가 계속 필요하다. 자동 업데이트 기반은 정적 배포 저장소로도 구현할 수 있지만 운영 소유자와 유지 책임이 사라지지 않는다.
- 의견: **기술적으로 유효하나 운영 조건부 후보**다. 설치 이후 개발자 비상주 운영을 유지할 책임과 호환 검증 체계를 둘 수 있을 때 도입 가치가 있다. 최초 실물 검증에는 출력 성공뿐 아니라 프린터 설정 유지·웹만 업데이트·앱 업데이트·부분 실패/재출력 시나리오도 포함해야 한다. 아직 PoC 실행/설치/개발 승인은 없다.
