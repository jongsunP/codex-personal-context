## 2. AI 공통 지침 초안

다음 기준은 FE가 환경에 한 번 연결합니다. PM·디자이너가 매 요청마다 props나 긴 개발 지침을 입력하는 방식으로 만들지 않습니다.

1. **요청을 먼저 확인합니다.** 대상 앱·사용자, 화면 목적, 필요한 정보와 동작, 기기·언어를 기존 대화와 요청에서 파악합니다. 화면의 의미나 기능이 달라질 정보가 빠졌다면 핵심 질문을 묶어 확인합니다. 이미 확인된 내용이나 사소한 간격까지 반복 질문하지 않습니다.
2. **실제 DLDS를 사용합니다.** 새 범용 UI는 `@dentlink/ui/dlds`에서 가져옵니다. `shared/ui` 전체나 주문폼·링크톡을 디자인시스템으로 취급하지 않습니다. 존재하는 입력·버튼·창을 임의의 HTML·새 라이브러리로 다시 만들지 않습니다.
3. **정확한 계약을 읽습니다.** 선택한 컴포넌트의 타입·구현·예제를 확인한 뒤 props와 기본값을 사용합니다. 다른 라이브러리에서 익숙한 속성을 추정하거나 모든 callback이 같은 형태라고 가정하지 않습니다.
4. **제품의 화면 구성 방법을 따릅니다.** Typography·테마와 대상 앱의 배치·반응형 방식을 참고합니다. 스타일은 Styled Components로 작성하고 스타일 전용 상태는 transient prop을 씁니다. DLOS 모음 화면의 사이드바·검사 패널 외형을 제품 화면 디자인으로 옮기지 않습니다.
5. **요청한 범위 안에서 구성합니다.** 기획·디자인 초안의 배치 선택은 기존 기준 안에서 진행하고 선택 근거를 남깁니다. 입력 항목·업무 기능·권한·이동·새 오류/Retry 동작을 요청 없이 추가하지 않습니다. 추가 제안은 구현할 내용과 구분해 보여줍니다.
6. **없는 UI는 구분합니다.** 기존 컴포넌트 조합으로 가능한지 먼저 확인합니다. 새 UI가 필요하면 이유·기존 조합의 한계·제안 범위를 설명합니다. 승인된 실험 초안은 화면 안에서 만들 수 있지만 공식 DLDS 등록이나 공통 기본값 변경은 별도 검토합니다.
7. **샘플과 제품 연결을 분리합니다.** 가상 데이터와 로컬 상태/callback으로 합의한 동작을 실행합니다. API·사용자 권한·업무 정책·분석 도구를 임의로 붙이지 않습니다. 재사용할 화면 코드는 UI와 실제 연결점을 분리합니다.
8. **실행하고 확인합니다.** 생성 파일이 검사·번들 대상에 들어있는지 확인하고 타입·lint·빌드·브라우저 화면과 요청한 동작을 검증합니다. 스크린샷만 만들거나 기존 컴포넌트 테스트 통과만으로 화면 구현 완료라고 하지 않습니다.
9. **수정 요청에서는 나머지를 보존합니다.** 요청한 부분을 수정하고 기존 입력값·동작·반응형에 영향이 없는지 확인합니다. 해결하려면 요구 변경·새 의존성·실제 데이터 접근이 필요한 경우 원인과 선택지를 보고합니다. 같은 오류를 반복하며 범위를 확대하지 않습니다.
10. **FE가 이어받을 결과를 남깁니다.** 실제 소스, 실행 방법, 사용한 DLDS, 샘플 상태, 수행한 검증과 미연결 사항을 전달합니다. 초안·실행 성공·제품 적용·배포를 서로 구분합니다.

### 특히 틀리기 쉬운 현재 코드 계약

전체 props 명세는 소스와 사용 안내를 조회합니다. 아래는 첫 지침에 포함할 핵심입니다.

- **Button:** 공개 DLDS의 `Button`은 `Button.refactor`이며 기본 `size=m`, `color=black`, `variant=filled`입니다. root `@dentlink/ui`의 기존 Button과 다릅니다. 갤러리의 초기 purple 선택은 기본값이 아닙니다. form 안에서 제출용이 아닌 버튼은 `type="button"`을 지정합니다.
- **TextInput·선택:** TextInput의 오류 표시는 `errorFocused`와 `errorMessage`를 함께 확인합니다. `SelectDropdown`은 `value/onChange`, Combobox 다중 선택은 `values/onValuesChange`, FilterDropdown은 배열 `value/onChange`입니다. `0`·`false`도 유효한 값입니다. Checkbox의 `checked`·`defaultChecked`를 혼용하지 않습니다.
- **날짜:** `DateField`는 `value`가 아니라 `defaultValue`를 받으며 callback은 날짜/문자열과 유효 여부를 전달합니다. `DateRangeFieldV2`는 `Date[]`를 사용합니다. 끝 날짜 제외·기간 차이 계산 등 기존 계약을 바꾸거나 달력 제한만으로 수동 입력 검증을 대체하지 않습니다.
- **창:** Modal은 `$isOpen`, Popup은 `isOpen`입니다. Modal의 `autoClose`는 배경 클릭 설정이며 Escape 설정이 아닙니다. `trapFocus` 기본값은 false입니다. 적용할 때 제목·초점 복귀·자식 Portal 범위를 확인하며 기존 사용처 전체에 일괄 적용하지 않습니다.
- **글자·간격:** Typography의 `variant`와 실제 테마를 사용합니다. 테마에는 전역 spacing scale이 없으므로 없는 토큰을 지어내지 않습니다. Clinic/Lab과 Admin의 폰트 파일·굵기 연결이 다르므로 숫자500만 보고 전체를 바꾸지 않습니다.
- **아이콘·문구:** 실제 공개 아이콘 이름을 조회해 사용합니다. 공통 UI의 기본 문구로 렌더된 것과 제품 번역이 연결된 것을 구분합니다. 문구 변경은 대상 언어·요구 범위에 맞춰 처리합니다.

## 3. 미리보기 기본 환경 구성안

**이미 있는 기반:** workspace의 실제 DLDS 코드, React/Vite, ThemeProvider, Pretendard·자간, `modal-root`·`portal-root`·`drawer-root`, 상태별 예제가 있습니다. 공개 npm 패키지가 아니므로 저장소 밖 서비스에서 바로 설치할 수 있다고 가정하지 않습니다.

**추가할 최소 구성:** 생성된 화면을 표시하는 진입점, 가상 데이터·callback, 생성 파일까지 포함하는 타입/lint/빌드 대상, 화면 확인·수정 절차입니다. 이후 비개발자가 요청·미리보기·수정을 수행할 접근 환경과 FE 전달 방식을 붙입니다.

- 현재 `pnpm dev:ui`는 고정된 DLDS 컴포넌트 모음입니다. 프롬프트 입력·AI 호출·생성 화면 표시·자동 수정·공유 기능은 없습니다.
- 대상 앱의 필요한 폰트·테마·Portal 환경만 구성합니다. 기존 AppProviders 전체를 복사하면 Next/router·API·분석 등 업무 환경도 섞입니다.
- 캔버스 너비 변경만으로 모바일 분기·Drawer를 검증하지 않습니다. 반응형은 실제 브라우저 viewport로, 모바일 Drawer 분기는 기기 에뮬레이션 등 모바일 환경으로 확인합니다.
- 첫 실행 방법은 기존 workspace를 활용하는 로컬 실험을 추천합니다. 생성 파일 위치·제공 도구·모델·비개발자 접근·호스팅은 구현 전 정합니다. 아직 새 경로나 제공 방식을 확정하지 않았습니다.

### 첫 시험 요청 예시

> 치과 서비스의 연락처 수정창을 만들어 주세요. 현재 국가와 휴대폰 번호를 보여주고 국가는 바꾸지 못하게 해 주세요. 번호를 수정하고 Save를 누르면 미리보기의 연락처가 바뀌고 창이 닫히면 됩니다. 번호의 숫자 입력·필수 검증은 현재 서비스 기준을 따릅니다. 실제 서버에는 저장하지 않고 샘플로 확인하고 싶습니다. 화면 문구는 기존 영어 서비스를 따르고, PC와 휴대폰에서 사용할 수 있게 해 주세요.

이것은 **시험용 제안 요구**입니다. 가상 사용자·국가 옵션·전화번호와 로컬 저장 callback만 사용합니다. 실제 사용자의 정보는 조회·수정하지 않습니다. 국가 변경·SMS 설정·새 Retry 버튼 등을 이 요청에 추가하지 않습니다.

### 함께 시험할 요청

- **정보가 부족한 요청:** “연락처 수정이 더 편하면 좋겠어요.” → 무엇이 불편한지와 유지/변경할 흐름을 확인합니다. 새 기능을 임의로 추가하지 않습니다.
- **후속 수정:** “입력 항목과 저장 동작은 유지하고, 좁은 화면에서도 입력칸과 Save가 잘리지 않게 해 주세요.” → 기존 입력·검증·저장을 보존한 채 좁은 화면을 다시 확인합니다.
- **DLDS에 없는 UI:** “전화번호를 직접 입력하는 대신 음성으로 받는 기능을 넣어 주세요.” → 기존 DLDS 지원 여부와 브라우저/권한/개인정보 처리가 필요한 범위를 설명하고 별도 기능 제안으로 구분합니다. 작동하지 않는 가짜 버튼을 완료 결과로 넣지 않습니다.
- **반복:** 같은 요청·코드 기준·샘플·도구 조건에서 여러 번 생성해 컴포넌트 선택과 요구 충족이 유지되는지 비교합니다. 횟수와 시간 한도는 첫 실행 비용을 본 뒤 정합니다.

**시험 방식도 구분합니다.** 기존 완성 화면 코드를 제공한 연결 시험은 실행 기반을 확인하는 근거입니다. 자연어 생성 품질을 평가할 때는 공통 기준·컴포넌트 자료·일반적인 화면 구성 예시를 제공하고, 대상 화면의 완성 코드를 그대로 답으로 주지 않는 별도 실행을 준비합니다. 실제 제공한 맥락을 기록해 결과를 과장하지 않습니다.

## 5. 검증과 FE 인계 기준

**코드·실행에서 확인할 것**

- 존재하는 DLDS import·props·토큰을 쓰는지, 업무 API나 요청 밖 기능을 넣지 않았는지 확인합니다.
- 생성 파일을 포함한 타입·lint·빌드가 통과하고 실제 브라우저에서 열려야 합니다. 필요한 Portal·폰트가 빠지거나 실행 오류가 남으면 완료로 보지 않습니다.
- 합의한 입력·선택·검증·저장·창 닫기와 후속 수정을 실행합니다. 반응형·키보드·중첩 창은 해당 화면에 존재하는 범위에서 확인합니다.

**화면 품질에서 확인할 것**

- 대상 앱의 글자·색·간격·정렬·정보 밀도, 긴 문구와 좁은 화면에서의 잘림을 확인합니다.
- 기존 제품은 구성 기준의 참고입니다. Figma 시안이 없는 화면에 존재하지 않는 목표 이미지와의 픽셀 일치를 약속하지 않습니다. 디자인 판단은 코드 검사만으로 대체하지 않습니다.

**FE가 이어받을 때 확인할 것**

- UI 컴포넌트와 화면 소스를 실제로 유지하며 샘플 데이터·callback을 제품 데이터와 동작으로 연결할 수 있어야 합니다.
- FE 수정량을 **UI 재작성 / 배치·스타일 보정 / 상태·동작 수정 / API·권한 연결**로 나눠 남깁니다. 원래 필요한 API 연결까지 AI 화면 생성 실패로 세지 않으며, UI를 대폭 다시 만든 결과를 재사용 성공이라고 하지 않습니다.
- 한 번 예쁘게 나온 결과뿐 아니라 모호한 요청의 질문, 반복 생성, 후속 수정 후의 보존, PM·디자이너의 요청·확인과 FE 전달까지 시험합니다. 실제 수정량·재사용 효과는 아직 미검증입니다.

### 기존 검사 명령의 적용 범위

아래는 현재 코드에서 확인한 명령입니다. 이번 문서 준비에서 실행하지 않았으며, 생성 파일이 아직 없으므로 생성 화면 통과 결과도 없습니다.

```sh
pnpm --filter @dentlink/ui exec tsc -p tsconfig.dlds-gallery.json --noEmit
pnpm --filter @dentlink/ui exec eslint --no-eslintrc --config .eslintrc.cjs dlds-gallery tests vitest.config.ts
pnpm --filter @dentlink/ui exec vite build
```

현재 타입/lint 대상은 모음 페이지 중심입니다. 다른 위치의 생성 파일을 자동 검사하지 않으며, Vite build도 진입점에 연결된 파일을 번들할 뿐 타입 검사를 대체하지 않습니다. 미리보기 위치를 정할 때 검사 대상과 진입점을 함께 연결해야 합니다. 기존 `pnpm test:ui`는 공통 UI 회귀 검사이며 새 화면의 요구 충족을 자동으로 증명하지 않습니다. 기본 UI 패키지 전체 타입 검사에는 기존 오류가 섞일 수 있으므로 기준 오류와 신규 오류를 구분합니다.

## 6. 다음 구현에서 정할 사항

1. 첫 연결 시험 후보와 샘플 동작을 확정합니다. 이 초안에서는 **Clinic 내 정보 수정 팝업**을 추천합니다.
2. 실제 DLDS가 실행되는 최소 미리보기와 검사 대상을 연결하고, 공통 지침을 읽는 방식으로 첫 생성을 시험합니다. 모델·도구·작업 브랜치와 결과 파일 위치는 착수 시 정합니다.
3. 실패한 항목을 근거로 기준을 수정한 뒤 전체 대표 화면·반복/수정 요청·FE 인계까지 넓힙니다.
4. 검증된 흐름을 PM·디자이너가 개발 설정 없이 사용할 환경으로 제공합니다. Figma 출력·요소 선택·시각 에디터는 그 이후 필요성을 판단합니다.
