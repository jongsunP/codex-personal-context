## 확인된 사실 — 사건 당시 관측

- 발생 시각은 2026-10-12 11:02경 KST. 사건 당시 네이티브 기록은 iPhone 15 / iOS 26.6.1, 설치 앱 2.2.4 build 1 / 적용 CodePush v81, 웹 1.87.0.1이다. 이후의 현재 배포 상태를 뜻하지 않는다.
- 주문 목록은 네이티브, 주문 상세는 웹뷰다. 양쪽 API는 디바이스에서 `api.dentlink.io`를 직접 호출한다. `portal.dentlink.io`는 웹 화면을 제공하며 이 API의 FE 서버 중계 경로는 없다.
- 같은 주문의 상세 진입을 3회 시도했다. 네이티브 주문·직원 API는 모두 200, 네이티브 토큰 갱신도 200이었다. 서버 직원 응답은 APPROVED / OWNER였다.
- 웹 RUM에서 두 번째·세 번째 시도의 올바른 주문 주소 진입 후 직원 API 실패와 `/403` 이동을 확인했다. 첫 시도의 웹 기록까지 모두 확보했다고 주장하지 않는다.
- 해당 웹뷰의 사용자·직원 등 제품 API 8건은 status 0, 소요 시간 3~8ms였다. 인증 정보를 쓰지 않는 Amplitude 설정 fetch 16건도 status 0, 1~12ms였다. 웹 홈으로 이동한 후에도 제품 API 실패가 이어졌다.
- 같은 웹뷰의 portal 화면 전환용 fetch 2건은 200, 약 225~228ms였다. 이는 실제 주문 내용 조회 성공의 증거와 구분한다. HTML·JS 실행과 이 200 응답은 웹뷰의 모든 통신이 실패했다는 설명을 낮춘다.
- 조회한 서버 로그에는 11:02:18·24·36의 네이티브 직원 GET이 있었다. CFNetwork User-Agent로 네이티브 요청을 구분했다. 실패 웹뷰 요청 시각인 11:02:25.915·38.010에 대응하는 기록은 해당 조회 범위에서 찾지 못했다.
- 보존된 APM에서도 같은 시각의 네이티브 직원 요청 200과 서버 처리 약 7.6ms를 확인했다. APM은 샘플링되며 전체 요청을 보장하지 않는다. OPTIONS도 현재 로그 조회에서 유무를 판정할 자료가 부족하다.
- 관측한 `orders_view`, `orderdetail_view`는 해당 기기의 iOS 네이티브 SDK가 보냈다. 상세 화면으로 전환할 때 전송하므로 웹 API·렌더링 성공을 보장하지 않는다. 웹에도 같은 이름의 이벤트가 있어 이름만으로 발송 플랫폼을 판단하지 않는다.

## 코드 해석과 결론의 한계

- 웹 `clinic/src/common/hocs/withAuthorization.tsx`의 catch는 API 통신 예외도 `/403`으로 처리하고 원본 오류 종류를 기록하지 않는다. 관측한 실패→403 흐름은 이 경로와 일치한다. 실제 catch 실행과 정확한 실패 원인을 런타임 오류 기록으로 확정한 것은 아니다.
- Return to home은 웹 403 화면의 버튼이다. 이 화면과 status 0만으로 서버의 실제 권한 거절이나 서버 미도달을 확정하지 않는다.
- status 0은 브라우저가 HTTP 응답 상태를 확보하지 못했다는 기록이다. 클라이언트 취소·네트워크 실패·CORS에 따른 응답 접근 제한·서버 앞단 차단 등을 추가로 구분해야 한다.
- 실제 직원 조회 경로인 shared `officeApi`는 오류를 reject하고, 권한 HOC는 기록 없이 403으로 전환한다. 설치된 Datadog Browser SDK 5.17.1에서는 실패 요청이 Resource에 기록돼도 Error 이벤트가 자동 생성되지 않을 수 있다. 현재 기록에 Axios 원본 오류가 없다는 점은 실패의 반증이 아니다.
- 앱 코드에서 해당 API를 직접 취소하거나 외부 origin을 차단하는 근거는 찾지 못했다. `/403`은 앱의 저장소 초기화·자동 reload 대상도 아니다. 일반 화면 재렌더가 모든 요청을 중단시켰다고 단정하지 않는다.
- 우선 후보는 해당 웹뷰의 통신 상태·기기/네트워크의 선택적 차단, 특정 조건의 CORS 사전 요청 또는 API 앞단 처리다. 제품 API와 Amplitude 설정 요청의 공통 원인은 미확정이다.
- 잘못된 주소·없는 주문·전역 서버 지연은 현재 근거상 후순위다. 웹뷰 토큰 전달이나 특정 앱·iOS 버전 문제는 완전히 배제하지 못했다. 특정 버전 결함·CORS·VPN/DNS 등을 원인으로 확정하거나 해결됐다고 보고하지 않는다.

## 추가 확인과 재개 조건

1. **BE·인프라:** 당시 IP·호스트·경로와 시계 오차를 고려해 GET/OPTIONS를 API 앞단 접근 로그까지 대조한다. 인증 전 요청에는 사용자 정보가 없을 수 있어 사용자 ID 필터는 제외한다. 응답 상태·차단 사유·Origin·사전 요청 헤더·CORS 응답 헤더가 필요하다.
2. **FE·앱:** 원본 error code/message, XHR 상태와 응답 주소, 페이지 주소, 토큰 존재 여부·직원 ID·버전을 기록하는 보강과 통신 실패/실제 권한 부족 구분을 검토한다. 현재는 제안이며 구현하지 않았다. 상세 네트워크 재현에는 검사 가능한 검증 빌드가 필요하고, 운영 앱이 바로 Safari Inspector에 표시된다고 가정하지 않는다.
3. **CS:** 재로그인 전에 동일 기기·계정·소속·주문으로 Safari vs 앱, Wi-Fi vs 모바일 데이터를 한 조건씩 비교하고 정확한 시각을 받는다. 복구 결과만으로 토큰이나 네트워크 원인을 단정하지 않는다.
4. 위 로그·재현 결과 또는 사용자 재개 요청이 오면 먼저 개인 컨텍스트를 pull하고 Notion/원본 자료 및 당시 코드와 실제 현재 상태를 다시 대조한다. 재개 요청만으로 제품 코드·Jira·배포 변경 권한을 확대하지 않는다.
