- **분석 목적과 현재 한계:** 기획의 제출률·주요 진입점·상세 옵션 사용 분석 의도는 확인했다. 현재 클릭 이벤트는 저장 성공, 최종 평가, 구체적 선택 사유를 직접 담지 않는다. 사유/댓글/이미지 1회 제한, 웹 단일 이미지 성공과 앱 선택 배치 전체 성공 차이는 문서에 상세 정의가 없다. 이를 임의 정책으로 확정하지 않고 집계 기준 확인 대상으로 기록했다.

### 신규·수정·재클릭·실패와 속성 해석

- **신규/수정 판정은 둘이다.** API는 `isPersisted`로 POST/PUT을 선택하고, 상세/편집 클릭 이벤트는 `hasDetails`(사유/댓글/첨부 존재)로 분기한다. Good/Bad만 이미 저장한 주문은 API로는 수정 대상이지만 `review_detail_click`이다. 피드백 최초 작성 건수와 `review_detail_click` 건수를 같다고 해석하면 안 된다([웹 adapter W21](https://github.com/Innvoaid/dentlink-client/blob/9084878eaa93ea4fe39df0f376afa4456c5fec55/clinic/src/services/feedback/feedback.adapter.ts#L103), [웹 mutation W22](https://github.com/Innvoaid/dentlink-client/blob/9084878eaa93ea4fe39df0f376afa4456c5fec55/clinic/src/services/feedback/feedback.query.ts#L133), [Office repository O19](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/services/feedback.repository.ts#L247)).
- 목록/배너 Good/Bad는 미평가 때만 표시한다. 성공 후 버튼이 상세/편집으로 바뀌므로 보통 같은 버튼 재클릭은 불가능하다. 실패 후 재시도는 다시 클릭을 기록한다. 웹은 버튼 `disabled`로 pending을 막고, Office native 목록은 추가 동기 ref 가드도 있다. 이 차이만으로 웹에서 실제 중복 전송이 발생한다고 확정하지 않았다.
- 상세 Good/Bad는 같은 값 선택·다른 값 변경 모두 수동 이벤트가 없다. Submit은 dirty 여부로 제한하지 않아 유효한 변경 없는 재제출도 호출 가능하다. 필수값 부족·500자 초과·업로드 중·저장 중은 Submit 이벤트 전에 차단한다. 저장 실패 후 재시도는 또 호출한다. 별도 피드백 저장 성공/실패 이벤트는 없다.
- `reviewdetail_select_reason`·`add_comments`·`img_upload`는 웹 drawer 재열기/다른 주문에서 ref를 초기화하고, native는 화면 mount 단위 ref다. 최초 성공/입력을 되돌리거나 첨부를 지워도 그 세션에서 이미 호출한 이벤트는 취소하지 않는다. 웹 첨부 성공 callback은 orderId를 비교하지만 닫힘 여부를 직접 검사하지 않으므로 닫기/취소와 성공 callback의 경합은 정적 코드만으로 배제하지 않았다. 재현된 결함으로 분류하지 않는다.
- **7개 `review*` 이벤트 모두 `orderId`, `source`, `entryPoint`, `platform`, `device`를 명시하지 않는다.** Good/Bad 이벤트에만 `feedbackType`이 있고 나머지 6개는 명시 속성이 없다. 사유 코드·댓글 길이·첨부 수·최종 평가·신규/수정 여부도 없다. wrapper가 이 값을 추가하지 않는다. native `entryPoint`/`orderId`는 `feedbackdetails_view.screen_params`에만 들어가며, 프로필에서 목록 진입 시 `screen_params`는 undefined일 수 있다.
- 따라서 “목록에서 Good → 상세에서 Bad로 변경 → Submit”은 수동 이벤트상 **Good 클릭 + Submit**만 남고 최종 Bad는 알 수 없다. 이는 코드로 확인된 분석 한계다. 최종 결과 분석이 요구된다면 승인 후 이벤트 범위/속성을 정해야 하며, 클릭 이벤트를 임의로 성공 이벤트로 바꾸지 않는다.
- 상세 클릭 이벤트는 UI가 보유한 `hasDetails`로 결정하므로 클릭 뒤 상세 재조회가 다른 내용을 반환하면 최신 서버 기준과 차이 날 수 있다. 과거 값이 실제 발생했다고 주장하지 않는다. 이벤트 자체에 주문/현재 값이 없어 이 차이를 해당 이벤트 속성만으로 교정할 수 없다.
- 첨부 삭제·첨부 picker 열기/취소·Photo/Camera/File 구분·비이미지 업로드·탭/페이지/새로고침·닫기/이탈의 **피드백 전용** 이벤트는 없다. Office 재사용 사진 picker의 `photo_click`은 상세가 `isPhotoSelectionTrackingEnabled={false}`를 넘겨 명시적으로 꺼 둔다([웹 첨부 W06](https://github.com/Innvoaid/dentlink-client/blob/9084878eaa93ea4fe39df0f376afa4456c5fec55/clinic/src/components/Feedback/FeedbackAttachmentUpload.tsx#L50), [native 상세 O20](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/features/feedback/screens/FeedbackDetailsScreen.tsx#L913), [picker O21](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/features/chat/components/ChatFileUploadBottomSheet.tsx#L51)). 없는 이벤트를 새로운 필수 요구사항으로 단정하지 않는다.
- 푸시는 FCM 처리에서 `landBy=push`와 `pushTitle`을 링크에 넣고 공통 navigation이 `push_click`을 호출한다. 동일 URL/목적지의 1.5초 중복 억제와 Android raw URL→FCM 보강 분기가 있으며, 피드백에 별도의 양OS 이벤트 이름 분기는 없다. `pushType`의 `1st Feedback`은 **최초 작성 사실이 아니라 orderId query 존재 여부**로 결정된다. Lab에도 공통 `push_click`은 있지만 Feedback 분류/실제 Feedback 화면은 없으며 잔존 enum만으로 구현이라 판단하지 않는다([FCM O32](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/configs/utils/fcmHandler.ts#L379), [Office 호출 O30](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/libs/useNavigationConfig.ts#L1329), [Lab 분류 L08](https://github.com/Innvoaid/dentlink-lab-app/blob/12cd290e4344065ac030f6a64696df4426a8b59c/src/libs/useNavigationConfig.ts#L161)).
- 직접 URL/딥링크 상세 진입은 클릭 handler를 통과하지 않으므로 `review_detail_click`/`review_edit_click` 없이 열릴 수 있다. Office 딥링크는 유효한 orderId가 있으면 `entryPoint:"deep-link"`로 상세에 바로 연결되고, 목록 호환 진입은 조회 후 상세로 이동한다([딥링크 O04](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/configs/utils/deepLink.ts#L110), [목록 호환 O22](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/features/feedback/screens/FeedbackListScreen.tsx#L455)). 조회는 공통 페이지뷰/native view로 구분해야 한다.

### WebView·중복·SDK 경로

1. Office `getDentlinkWebURL()`은 APP_ENV에 따른 Office portal, Lab은 Lab URL을 고른다. 7. 웹과 native는 로그인 user ID를 문자열로 identify하고 `service_type` 등 user properties를 설정한다. 이는 위 이벤트의 명시 source/platform/orderId와 별개다. native는 deviceId/sessionId를 직접 설정하지만 조사한 WebView 인증/bridge에는 Amplitude device/session ID 동기화가 없다. **앱에서 시작한 피드백 흐름도 browser SDK 이벤트와 RN SDK 이벤트가 섞인다.** 실제 프로젝트 키 동일성·세션 연결·자동 플랫폼 판정·최종 수집값은 미확인이다([웹 identify W27](https://github.com/Innvoaid/dentlink-client/blob/9084878eaa93ea4fe39df0f376afa4456c5fec55/clinic/src/pages/_app.tsx#L343), [Office identify O25](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/configs/utils/amplitude.ts#L71), [인증 전송 O28](https://github.com/Innvoaid/dentlink-app/blob/dd9fc9a2812b1eb98866b97a5f38451e1a546fd5/src/features/common/components/DentlinkWebView.tsx#L515)).
